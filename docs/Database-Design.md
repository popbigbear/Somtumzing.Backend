# Somtum Zabb Delivery — Database Design

**Document status:** Draft 0.1 — design rules remain provisional; schema applied to local PostgreSQL
**Database:** PostgreSQL
**Scope:** Target data model for the APIs in `API-Specification.md`. Migration `20261006084101_CreateGameDataSchema` has been applied to the local database configured by `.env`; production was not modified.

## 1. Design principles

1. Every table has a database-generated GUID/UUID primary key, a unique externally presentable `Code`, and the required audit/status columns:
   - `PK`
   - `Code`
   - `CreatedDate`
   - `CreatedBy`
   - `UpdatedDate`
   - `UpdatedBy`
   - `Status`
2. Internal relationships use database-generated `UUID` PK/FK values. Public APIs, reports, logs, and support workflows use `Code`; internal PK values are not exposed.
3. Valuable state (wallets, progression, session/order results, challenge results, and match results) is written by backend transactions, not accepted as an authoritative client total.
4. Historical financial/game outcomes are append-only. Corrections are represented by compensating records, not edits to posted history.
5. Static catalog records are versioned or status-controlled. A session/run/match pins the ruleset/config version it started with.
6. All timestamps are stored as `TIMESTAMPTZ` in UTC.

## 2. Standard columns on every table

The following columns are present on **every table listed in this design**, including lookup, bridge, ledger, and technical tables. Domain-specific columns are listed in the table catalogue.

| Column | PostgreSQL type | Null | Rule |
|---|---|---:|---|
| `PK` | `UUID DEFAULT gen_random_uuid()` | No | Primary key generated by PostgreSQL. Never supplied by clients. |
| `Code` | `VARCHAR(40)` | No | Unique externally presentable identifier; assigned in the database. |
| `CreatedDate` | `TIMESTAMPTZ` | No | Database UTC timestamp at insert. |
| `CreatedBy` | `UUID` | Yes | FK to `Users.PK`; null only for system/bootstrap-created records. |
| `UpdatedDate` | `TIMESTAMPTZ` | No | Set on insert and maintained on every mutable-row update by a database trigger. |
| `UpdatedBy` | `UUID` | Yes | FK to `Users.PK`; null only for system/bootstrap jobs. |
| `Status` | `VARCHAR(24)` | No | Domain lifecycle state, validated by a table-specific check constraint. |

Recommended defaults are `CreatedDate = transaction_timestamp()`, `UpdatedDate = transaction_timestamp()`, and `Status` set explicitly to the domain's initial state. Database triggers should reject application-supplied values for `PK`/`Code` and maintain `UpdatedDate`; the application provides actor identity for `CreatedBy`/`UpdatedBy`.

### 2.1 Audit actor rules

- `CreatedBy`/`UpdatedBy` reference the internal user PK, never the external `Code`.
- Guest self-registration and pre-user bootstrap records may have `CreatedBy = NULL`.
- For system operations (retention, matchmaker, scheduled challenge creation), use `NULL` or a dedicated service actor row consistently; do not impersonate a player.
- Immutable event/ledger rows still contain all standard columns. Their update trigger rejects changes to business fields; `UpdatedDate`/`UpdatedBy` remain equal to creation metadata. Retention deletion of expired audit rows is a controlled exception.
- Foreign keys from the shared audit columns use `ON DELETE RESTRICT`; user history must not disappear by deleting an actor account.

## 3. Primary key and public Code design

### 3.1 Primary key

Use PostgreSQL `UUID` for every `PK`, with `gen_random_uuid()` as the database default. All FK columns use `UUID` and reference the corresponding `PK`. The API and application must not accept a caller-supplied PK as proof of identity or authorization.

This matches the current prototype's GUID-based ASP.NET Identity user keys and refresh-token IDs. New tables should follow the same UUID convention so user ownership, JWT subjects, and API player IDs remain consistent.

### 3.2 Code format

Follow the supplied member-code pattern:

```text
<EntityPrefix><YYMM><TableCode><MonthlySequence>
```

Recommended monthly sequence width is **six digits**, to allow up to 999,999 records per table/month:

```text
User2610A000001
```

This keeps the requested `User2610A001` shape while avoiding a practical 999-members-per-month limit. The first example's `A` is the stable table/entity code for Users. Codes are identifiers for display/reference, not secrets or authorization credentials.

### 3.3 Database-side allocation

Use a PostgreSQL `CodeCounters` table keyed by `(PeriodYYMM, TableCode)` with an atomic `INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING` allocator inside the same transaction as the new row insert. The database constructs the Code from the entity prefix, UTC `YYMM`, table code, and returned counter. Add a unique constraint on every table's `Code`. A counter value allocated by a transaction that rolls back was never committed or exposed, so it may be allocated again; once a Code is committed and externally visible, it must never be reused.

`CodeCounters` itself also carries all standard columns and has a unique technical `Code` derived from its natural counter key, for example `Sequence2610A` for the Users counter in October 2026. It does not recursively consume a monthly counter. A counter row is operational metadata, not a player/report code.

Table/entity code allocation must be centralized and immutable. It must not be generated with `MAX(Code) + 1` without a lock, or with application-side counters. Use a fixed allow-list of prefixes/table codes in database code; never interpolate an untrusted table name.

> **Decision note:** `YYMM` follows the example. This repeats after 100 years. The unique Code constraint prevents silent collision; if Code must be mathematically unique over a longer retention horizon, prefer `YYYYMM` in the format before implementation.

## 4. Table catalogue

The standard columns in section 2 are included in **each** row below. Domain field lists omit those seven shared columns for readability.

`PK` is the primary key; each table also has `UNIQUE (Code)`. All relationship columns ending in `PK` are internal `UUID` foreign keys. `BIGINT` remains appropriate for counters, sequence values, and concurrency versions; it is not used for PK/FK columns.

ASP.NET Identity owns the logical `Users`, `Roles`, and `UserRoles` records. `Users` uses the physical table name `Users`; the Identity role and join tables retain the framework names `AspNetRoles` and `AspNetUserRoles` to preserve Identity conventions. Their primary keys remain GUIDs (the Identity user/role key property is physically named `Id`); `AspNetUserRoles` has the required surrogate GUID `PK` and a unique `(UserPK, RolePK)` pair. Identity-only claims, logins, and token tables are framework support tables rather than business tables in this catalogue.

## 5. Relationship summary

- `Users` 1—many `RefreshTokens`, `GameSessions`, `Wallets`, `ChallengeRuns`, `MatchParticipants`, `PlayerUpgrades`, and `PlayerLoadouts`.
- `Users` many—many `Roles` through `UserRoles`.
- `Stages` 1—many immutable `StageConfigs`; player completion is stored in `PlayerStageProgress`.
- `GameSessions` 1—many `Orders` and `ChaosEventInstances`; an order has at most one canonical `OrderResult`.
- `Wallets` 1—many immutable `WalletTransactions`.
- `Challenges` 1—many `ChallengeRuns`; accepted runs are the source for leaderboard queries.
- `Matches` 1—many `MatchParticipants`, `MatchActions`, `MatchResults`, and `MatchSabotageEvents`.
- `PlayerLoadouts` many—many `SabotageCards` through `PlayerLoadoutCards`.
- `AuditLogEntries` and ledger/event snapshots preserve external Codes and display identifiers, while FK values preserve internal relationships.

## 6. Status and lifecycle guidance

`Status` is required on every table but is **not** a universal boolean. Each table has a constrained domain-specific state listed above. Use status for lifecycle, not arbitrary free-form comments:

- Catalogs: `DRAFT -> PUBLISHED -> RETIRED`.
- Sessions: `ACTIVE -> COMPLETED -> SETTLED`, with explicit `ABANDONED`/`INVALID` outcomes.
- Event instances: `WARNING -> ACTIVE/RESOLVED/FAILED/EXPIRED`.
- Wallet transactions and match actions/results: append-only terminal states; corrections use reversal/invalidation records.
- User suspension uses `Users.Status = SUSPENDED`, suspension metadata, and security-stamp rotation. Reactivation returns to `ACTIVE`.

Status transitions are validated in application services and, for critical invariants, reinforced with database constraints/triggers.

## 7. Index and constraint baseline

In addition to every table's PK and unique Code:

- Create indexes on every FK used for joins/deletes; PostgreSQL does not automatically index the referencing side.
- Unique business keys: normalized user names, catalog keys/version, `(UserPK, CurrencyCode)`, per-session order sequence, per-match participant sequence, and idempotency scope/key.
- Index common player-history access paths: sessions by `(UserPK, StartedDate DESC)`, transactions by `(WalletPK, CreatedDate DESC)`, audit by `(OccurredDate DESC)`, challenge runs by `(ChallengePK, Status, CalculatedScore DESC)`, match participants by `(UserPK, JoinedDate DESC)`.
- Use partial indexes for active sessions, active refresh tokens, open queue tickets (if queue storage is added), and published catalog records where query patterns justify them.
- Validate non-negative values, percentages/rates, enum/status domains, date ordering, and positive sequence values with `CHECK` constraints.
- Avoid cascading deletes for gameplay history, wallet ledger, audit records, and match/challenge history.

## 9. Migration and compatibility notes

1. The local configured database has the target tables from migration `20261006084101_CreateGameDataSchema`; production has not been changed.
2. The migration preserves existing Identity and audit data, adds standard `Code`/audit/status columns, and uses UUID PK/FK values; no GUID-to-BIGINT conversion is required.
3. Existing actor metadata that could not be recovered remains null; the migration does not invent a human administrator as creator.
4. Future schema changes must use versioned migrations and be validated against a copy of current PostgreSQL data before production deployment.

## 10. Decisions required before production approval

- Review the monthly `YYMM` six-digit Code policy, UTC month boundary, stable table-code registry, and counter reset behavior before external Codes are issued in production.
- Confirm whether `CreatedBy`/`UpdatedBy` may be null for system/bootstrap operations.
- Approve status values and soft-delete versus physical-delete policy per entity.
- Confirm the initial product release's required tables: casual only, or include challenge/PVP tables before those features ship.
- Finalize economic, star, event, challenge, and competitive rules before treating provisional fields/calculations as authoritative.
- Confirm audit retention, ledger retention, and privacy/deletion policy.
- Define paid-currency receipt validation before adding platform purchase tables.

The local migration implements UUID PK/FK values and the seven shared fields for the designed tables; changing those structural policies now requires a follow-up migration. See [SDS-Architecture.md](./SDS-Architecture.md) for deployment and runtime assumptions.
